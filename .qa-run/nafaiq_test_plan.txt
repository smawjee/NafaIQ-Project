1 Introduction
1.1 Purpose
This document is the master test plan for the NafaIQ platform. It defines what is tested, at which
level, with which tools and data, in which environments, and how results and defects are recorded.
It is the first of the five QA-week deliverables and the frame of reference for the other four:
1. Test plan — this document.
2. Test cases covering all features — NafaIQ_Test_Cases_.xlsx: 654 cases across 25
feature modules plus the automated-journey results sheet.
3. Automated end-to-end test cases—thePlaywrightsuite(@nafaiq/e2e): 228testsin20
files across three browser projects, wired into CI and a nightly run, with a live failure-replay
harness (Section 6).
4. Bugs reported in Jira — defects filed to project KAN under a fixed reporting convention
(Section 13).
5. API tasks — two Postman collections: a complete 178-operation API catalog and a
68-request scripted end-to-end QA suite (Section 7).
1.2 Product overview
NafaIQ is a Pakistan-focused investing and personal-finance product covering live PSX market
data and analysis (signals V4), portfolio tracking, personal finance (transactions, budgets, bills,
goals, zakat), price/budget/goal alerts, notifications, an AI assistant and AI reports, a learning
hub with quizzes and an AI tutor, and an admin subsystem. It ships as a React web app, an Expo
(React Native) mobile app, and a FastAPI backend on a Supabase (PostgreSQL) database. The
interface is bilingual (English and right-to-left Urdu).

4 Unit and component testing
• Backend — pytest: 1457 passed, 4 skipped at plan time, across 144 test files. API
routes are exercised offline through dependency overrides and fake repositories; live-database
tests auto-skip when credentials are absent so CI never depends on Supabase.
• Web — Vitest with Testing Library and MSW: 179 tests in 18 files covering components,
hooks, Redux slices and API contracts.
• Mobile — Jest (jest-expo) with React Native Testing Library: 121 tests in 19 suites;
every screen test also asserts accessibility roles/labels per the mobile conventions.
Coverage is risk-ranked rather than exhaustive: money paths (portfolio arithmetic, finance
summaries, zakat), authentication and authorization, alert evaluation, and the AI quota/refresh
invariants take precedence over cosmetic rendering.
5 Integration and contract testing
Backend route→service→repository wiring is tested with the same offline override pattern used at
unit level, extended to whole-request flows:
• Cross-user isolation — every owned resource is probed with another user’s identity; the
expected result is a scoped 404, never a 403 that confirms existence.
• Error taxonomy—401/403/404/422/429contractsareassertedperroutefamily, including
the exact 401 messages the client refresh flow distinguishes.
• Pagination and boundary edges — empty datasets, last-page behaviour, inclusive
boundaries (e.g. the zakat nisab threshold).
• Frontend contracts — web and mobile API mocks are generated from the real backend
response schemas, so a backend field rename fails a frontend test rather than production.
This guard exists because the finance-summary contract drifted once before QA week.
• Policy middleware — CORS is pinned by test: allowed production and loopback origins,
and anchored-regex rejection of localhost.evil.com-style suffix attacks.

6.1 Design rules
All of the following are load-bearing for determinism:
• Journeys only — every spec is a user journey (open, act, observe on the destination page),
asserted with web-first matchers on structure rather than polled market values.
• One real login — a setup project signs in once with the demo account and saves storage
state; only the Supabase session keys are persisted so no spec leaks app state into the next.
• Deterministic AI — AI, assistant, tutor and report endpoints are stubbed with canned
responses in the exact streaming (SSE) framing the client parses.
• Console guard — any unexpected browser console error fails the test; known product bugs
are allow-listed with a remove-when-fixed note tied to their Jira key.
• Auth-settle guard — no interaction starts until the auth-resolution overlay has cleared,
eliminating the swallowed-tap class of mobile flake (root cause of an early Pixel 7 defect).
• Demo-account safety — demo-user writes live entirely in local state; browser journeys
therefore never mutate shared backend data.
6.2 Live failure replay
A hard failure in the automated suite can be reproduced in front of the tester without manual
setup. pnpm test:e2e:live runs the full suite and, on the first hard failure, launches a headed
Chromium, signs in through the visible NafaIQ form using the stored demo credentials, and
re-executes the failing journey:
• If the failure reproduces, Playwright pauses indefinitely with the browser and Inspector
open at the failure state for live debugging.
• If it passes (a flake), the end state stays visible for five seconds and the browser closes.
pnpm test:e2e:replay replays any chosen failure from the latest JSON report by index or by
fingerprint. Replay mode disables traces and uses only the console reporter so the demo password
never lands in an artefact, and the original suite report is not overwritten.
7 API testing (Postman)
Two collections, kept in postman/ with Local and Dev environments:
• NafaIQ API — Complete Catalog: all 178 FastAPI operations, generated from the
live OpenAPI schema and organised by the 27 API areas (finance, portfolio, signals-v4,
admin, ...). Every request carries an assertion script; write requests are prefixed REVIEW
BEFORE SEND. This is the discovery and manual-inspection surface.
• NafaIQ API — End-to-End QA: 68 scripted requests in nine ordered journey folders
(setup/authentication,publicmarket,portfolio,watchlist,personalfinance,goals/budgets/bills,
alerts and notifications, negative and authorization tests, optional AI). Requests chain dy-
namically captured IDs, assert on status and body, and clean up created records where the
API supports it, so the collection is re-runnable and presentation-safe.
The catalog is also the coverage yardstick: it exposed that only ∼40 of 155 user-facing endpoints
had cases before the expansion pass, which drove the creation of the 13 newest workbook modules.

8 Manual, exploratory and adversarial testing
Cases that automation cannot decide are executed manually against a live local backend with real
JWTs, with observed evidence recorded in the workbook’s Actual Result column. The adversarial
pass focused on: security and authorization (RBAC on all admin endpoints, IDOR across two real
accounts, credential-scope confusion, token error hygiene), data integrity (zakat nisab authority,
clamping and boundaries, portfolio arithmetic reconciliation, cost-averaging), input validation
(impossible dates, negative quantities, oversell), and AI guardrails (write-confirmation, cross-user
data requests, Roman-Urdu queries). Destructive probes were pointed at disposable records or
deliberately blocked (e.g. the untested bulk-delete endpoint, TC-DATA-20, was not fired at the
shared demo account).
9 Test design and documentation
All manual and API test cases live in NafaIQ_Test_Cases_.xlsx:
• One sheet per module, uniform columns: ID, module, scenario, preconditions, steps, test
data, expected result, actual result, status, priority.
• Statuses: Pass, Fail, Partial, Blocked. A Blocked case is never left bare — its Actual Result
states exactly what it needs (device, admin account, market window, failure injection, seeded
data, human judgement). Nothing is marked Pass without recorded evidence.
• Priorities: P1 (core money paths, security, data integrity) through P4 (cosmetic). Current
spread: 221 P1, 211 P2, 66 P3, 7 P4.
• E2E Journey Results sheet: one row per automated journey execution (149 rows =
journeys × browser projects), carrying the automation source file, evidence path, run commit
and timestamp.
• Execution Summary sheet: run metadata, defect focus, and the audit trail of each
execution pass.
Traceability is bidirectional: automated cases name their spec file in the workbook row, and
defects name their test case in Jira.

10.2 Prioritisation under the five-day timebox
A five-day box inverts the usual estimation question: not how long will full coverage take, but how
much coverage fits, in what order. The answer is risk-first, encoded in every workbook row as a
priority:
Priority Cases Definition Timebox rule
P1 221 Money paths, security, authorization, data integrity executed first, never cut
(zakat, portfolio arithmetic)
P2 211 Core feature behaviour and validation executed after P1
P3 66 Secondary flows, cosmetic states as time allows
P4 7 Nice-to-have polish only if idle
Two consequences of this ordering are visible in the results: every filed defect (Section 13) came
out of a P1/P2 case, and the cases that ran out of runway are concentrated in the lower priorities
and in the resource-blocked bucket. The 233 Blocked cases — each annotated with the exact
resource it needs (device, admin window, market hours, failure injection) — are deliberately
retained as the costed input for the next cycle’s estimate rather than being dropped from scope.
11 Test environment and data
• Local stack — Vite dev server (web) + uvicorn (backend) + Supabase project; this is what
Playwright boots and what manual API execution targeted (127.0.0.1:8000).
• Deployed — backend on Railway, web on Vercel; the Postman Dev environment and an
E2E_API_URL escape hatch point automation at it.
• Test identities — the shared demo account (read-mostly by design; its writes stay
client-side), a second real account for cross-user/IDOR checks, a purpose-made QA
super-admin (role granted in the database, proving roles are DB-resolved rather than
token-derived), and disposable targets for destructive operations. The demo account is
deliberately not an admin, because several cases assert it is refused.
• Data hygiene — every server-side write in manual execution went to a throwaway record
and was cleaned up; the demo baseline (net worth 164,467 across 3 holdings) was re-verified
identical after the pass.
12 Continuous integration and nightly runs
• ci.yml — on every pull request and push: lint/typecheck, web unit, mobile unit, back-
end tests, and the two Chromium E2E projects, converging on a single required check
(ci-required) that branch protection and deploy gates key on.
• nightly-e2e.yml — weekdays 08:00 PKT (before PSX opens): the full three-project matrix
including the Pixel 7 mobile viewport, which is deliberately off the merge path. The nightly
always checks out the dev branch (the integration branch), so a green nightly means
anything promoted dev→main is already QA-tested; a manual dispatch can override the ref.
• Branchflow—featurebranches→dev(integration)→main(production),withci-required
green as the promotion condition.

13 Defect management
Defects are filed in Jira project KAN as they are found, under a fixed convention:
• Title: plain words stating what is broken and where.
• Description: exactlythreeparts—Issue (1–2sentences),Steps (shortreproductionbullets),
Expected (1–2 sentences). Machine context (fingerprints, evidence paths, repro commands)
goes in labels or a comment, never the description.
• Severity is judged by user impact and data/monetary risk; religiously sensitive computation
(zakat) is automatically high.
• Automated triage: a runner parses the Playwright JSON report and files hard failures to
KAN with a stable fingerprint label per failure, so re-occurrences comment on the existing
ticket instead of duplicating it; infrastructure failures collapse to a single ticket, and a flood
of new fingerprints halts for human confirmation.

14 Entry and exit criteria
Entry (per execution pass): the build under test runs locally end to end; test data baseline
recorded; required identities available.
Exit (met at plan time):
• Every workbook case carries a real result or a specific blocking reason — no case left silently
unexecuted.
• All automated suites green: backend 1457 passed, web 179, mobile 121, Playwright 228
executions across three projects (latest nightly: all three projects passing).
• No open Highest/High defect without a fix or an explicit product decision pending (sole
remaining Fail: KAN-55, awaiting a gating decision).
• CI and nightly gates active on the integration branch.
Suspension: execution against shared data suspends immediately if a probe mutates the shared
demo baseline; the baseline is restored and verified before resuming (exercised once during the
pass, restored to the exact prior state).
