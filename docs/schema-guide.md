## 1. Schema Philosophy

The NafaIQ database is a **PostgreSQL 14** schema hosted on Supabase. It follows a few core principles:

### 1.1 Two categories of tables

| Category | Rules | Examples |
|---|---|---|
| **User-owned** | Has a `user_id FK → auth.users(id)`. RLS enforces `auth.uid() = user_id`. CASCADE on delete. | `profiles`, `user_watchlist`, `price_alerts`, `psx_portfolios`, `finance_*`, `ai_*` |
| **Public/shared** | No user ownership. RLS = `USING (true)` for SELECT. Service_role writes. | `psx_market_snapshot`, `psx_ohlcv`, `psx_fundamentals`, `psx_profile`, etc. |

**Why?** Stock prices are the same for everyone — duplicating 495 rows per user would be wasteful and impossible to keep consistent. User preferences (watchlists, portfolios, chat history) are private per user.

### 1.2 Surrogate vs natural keys

| Approach | Used for | Rationale |
|---|---|---|
| `bigint GENERATED BY DEFAULT AS IDENTITY` PK | Most tables (watchlist, alerts, portfolios, transactions, etc.) | Efficient B-tree index, Supabase Realtime compatibility, PostgREST convention |
| `text PRIMARY KEY` (natural key) | `psx_fundamentals`, `psx_profile`, `psx_signals`, `plan_features`, `feature_flags` | Business key is inherently unique and stable; no child table needs a FK reference |
| Composite PK (natural) | `psx_index_eod (code, date)`, `psx_watchlist_v1 (user_id, symbol)`, `ai_usage (user_id, day)`, `fx_rates (base, quote, date)` | The natural combination is guaranteed unique; no need for a surrogate identifier |
| `uuid PK` (matches auth) | `profiles` | 1:1 with `auth.users(id)` — user ID IS the profile ID |

### 1.3 v1 vs v2 coexistence

Two generations of watchlist and alert tables exist:

```
psx_watchlist (v1)  ── composite PK, older column names
user_watchlist (v2) ── surrogate bigint id PK, cleaner schema

psx_alerts (v1)     ── type + condition + threshold columns
price_alerts (v2)   ── condition + price, CHECK constraint, triggered_at
```

The v1 tables are safe to drop in Phase 1 cleanup — frontend uses only v2.

### 1.4 Logical vs declared foreign keys

Only 8 FKs are actually declared in SQL (the auth → user-owned tables chain). The 12 relationships from `psx_market_snapshot` to its child tables are **logical** — enforced at the application layer by the Python service, not by a database constraint.

**Why:** Backfill scenarios insert OHLCV rows before the corresponding snapshot row exists. Staging data (old announcements, delisted stock dividends) references symbols not in the active trading list. FK constraints would block these operations.

**Recommended Phase 1:** Add explicit FKs now that the pipeline is stable.

## 3. Auth & Profile

### 3.1 `auth.users` — Supabase-managed

**Not a table we create.** Supabase Auth handles this automatically on signup. Our code reads from it via the Supabase JS client (`supabase.auth.getUser()`).

**Key columns we depend on:**

| Column | Type | Purpose |
|---|---|---|
| `id` | `uuid` | User's unique identifier. Used as FK in every user-owned table. |
| `email` | `text` | Login identity. Used for Gravatar fallback if no avatar_url. |
| `created_at` | `timestamptz` | Account creation date. |
| `raw_user_meta_data` | `jsonb` | Stores `display_name` and `avatar_url` from OAuth providers or signup form. |

**Trigger:** `on_auth_user_created` fires `handle_new_user()` which inserts one row into `profiles`.

**Why we don't add columns to `auth.users`:** This is a Supabase-managed table. Any columns we add could be wiped on Supabase version upgrades. Instead, we put user-specific data in `profiles` which is our own table.

### 3.2 `profiles` — User profile (1:1 with auth)

**Purpose:** Stores user-facing profile data and plan information. Every auth user gets exactly one profile row, auto-created by a trigger.

**Why it's 1:1 (not embedded in auth.users):** We need to add columns (`phone`, `mfa_enabled`, `onboarding_complete` in Phase 7) that don't belong in the auth table. Keeping a separate table also means Supabase can manage auth independently from our schema.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `uuid` | NO | — | PK. FK → `auth.users(id) ON DELETE CASCADE`. Value = user's auth ID. |
| `display_name` | `text` | YES | `null` | From OAuth provider or user-set. Used in UI headers and notifications. |
| `plan` | `text` | NO | `'Free'` | `Free` / `Pro` / `Premium` / `Admin`. Gates feature access. |
| `avatar_url` | `text` | YES | `null` | From Google/GitHub OAuth, or upload. |
| `created_at` | `timestamptz` | NO | `now()` | |
| `updated_at` | `timestamptz` | NO | `now()` | Auto-updated by `update_profiles_updated_at` trigger. |

**Business rules:**
- Every `auth.users` row MUST have exactly one `profiles` row (enforced by trigger).
- Deleting an auth user CASCADES to delete the profile.
- `plan` determines feature limits (queried from `plan_features` table in Phase 8).

**RLS:**
```sql
SELECT: USING (auth.uid() = id)
INSERT: WITH CHECK (auth.uid() = id)
UPDATE: USING (auth.uid() = id) WITH CHECK (auth.uid() = id)
```

**Planned additions (Phase 7):**
- `phone TEXT` — for SMS notifications
- `mfa_enabled BOOLEAN` — multi-factor auth preference
- `onboarding_complete BOOLEAN` — onboarding wizard status

## 4. PSX Market Data (Public)

All tables in this section share:
- **RLS:** `FOR SELECT USING (true)` — anyone can read
- **GRANTS:** `SELECT TO anon, authenticated`; `ALL TO service_role`
- **Writes:** Only the Python FastAPI service (via `supabase.service_role` key)

### 4.1 `psx_market_snapshot` — Live prices

**The central table of the PSX module.** Every other PSX table references it by `symbol`. Updated every 5 seconds by the DPS refresh job, with live price patches from the AhleTrade poller.

**Why `bigint id PK` and not `text symbol PK`:**
- Supabase Realtime requires a single-column PK for WAL-based change tracking.
- `bigint` PKs are faster for B-tree traversal at scale.
- If PSX renames a ticker, only the `symbol` column changes — no FK cascading needed.
- `UNIQUE(symbol)` still exists for business-key integrity and `ON CONFLICT (symbol) DO UPDATE`.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | NO | `GENERATED BY DEFAULT AS IDENTITY` | PK. Never used directly by application code — exists for Realtime. |
| `symbol` | `text` | NO | — | **UNIQUE**. PSX ticker symbol (e.g., `HBL`, `EFERT`, `PIOC`). Canonical business key. |
| `price` | `numeric(12,2)` | YES | `null` | Last traded price. Precision: 2 decimal places (paise). |
| `change` | `numeric(12,2)` | YES | `null` | Absolute change from previous close. |
| `change_pct` | `numeric(8,4)` | YES | `null` | Percentage change from previous close. Computed by DPS, stored as-is. |
| `volume` | `bigint` | YES | `0` | Total volume for the current session. |
| `day_high` | `numeric(12,2)` | YES | `null` | Session high price. |
| `day_low` | `numeric(12,2)` | YES | `null` | Session low price. |
| `refreshed_at` | `timestamptz` | NO | `now()` | When this row was last updated by the Python service. |

**Indexes:**
- `idx_psx_ms_sym(symbol)` — symbol lookup (used by every child table join)
- `idx_psx_ms_refreshed(refreshed_at DESC)` — freshness check (Python service checks if cache is stale)

**Realtime:** `ALTER PUBLICATION supabase_realtime ADD TABLE` — every upsert is broadcast to subscribed clients.

**Data flow:**
```
DPS market-watch HTML (5s) ──┐
                              ├──► Python service (bulk upsert) ──► psx_market_snapshot
AhleTrade feed (3s) ─────────┘         │
                                       ▼
                              Supabase Realtime broadcasts to frontend
```

**Sample row:**
```
id=12345, symbol='HBL', price=142.50, change=+1.25, change_pct=0.88,
volume=1250000, day_high=143.00, day_low=141.25, refreshed_at='2026-07-07T10:30:00+05:00'
```

### 4.2 `psx_ohlcv` — Daily OHLCV history

**Purpose:** Stores daily open, high, low, close, volume for every PSX symbol. Used for candlestick charts, technical indicators, and ML feature computation.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | NO | `GENERATED BY DEFAULT AS IDENTITY` | PK |
| `symbol` | `text` | NO | — | Logical FK to `psx_market_snapshot.symbol` |
| `date` | `date` | NO | — | Trading date |
| `open` | `numeric(12,2)` | YES | `0` | Session open price |
| `high` | `numeric(12,2)` | YES | `0` | Session high price |
| `low` | `numeric(12,2)` | YES | `0` | Session low price |
| `close` | `numeric(12,2)` | YES | `0` | Session close price |
| `volume` | `bigint` | YES | `0` | Session volume |

**Uniqueness:** `UNIQUE(symbol, date)` — one row per symbol per day.

**Index:** `idx_psx_ohlcv_sym_date(symbol, date)` — covers the UNIQUE constraint and is used for the common query pattern `SELECT * FROM psx_ohlcv WHERE symbol = 'HBL' ORDER BY date DESC LIMIT 250`.

**Data volume:** ~495 symbols × 250 trading days/year × 10 years = ~1.2M rows. With `bigint id` (8 bytes) + `text symbol` (~4-8 bytes avg) + `date` (4 bytes) + 5 × `numeric(12,2)` (~8 bytes each) + `bigint volume` (8 bytes) ≈ 70 bytes/row × 1.2M ≈ 84 MB. Small enough to fit in memory on any Postgres instance.

**Backfill strategy:** The `job_backfill_history` job runs daily at 02:00 PKT and fetches OHLCV for all symbols from DPS, bulk-upserting with `ON CONFLICT (symbol, date) DO UPDATE`. New symbols get their full history inserted; existing rows are updated if DPS revised the data (rare).

### 4.3 `psx_fundamentals` — Company fundamentals (1:1 with snapshot)

**Purpose:** Cached fundamental data for each stock. Updated weekly by the Python service.

**Why text PK (not surrogate):** The `symbol` is the natural and only business key. No other table references `psx_fundamentals` by FK. The 1:1 relationship with `psx_market_snapshot` is implicit (same symbol).

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `symbol` | `text` | NO | — | PK. Same value as `psx_market_snapshot.symbol`. |
| `eps` | `numeric(12,2)` | YES | `null` | Earnings Per Share (TTM). |
| `pe` | `numeric(8,2)` | YES | `null` | Price-to-Earnings ratio. PE = price / EPS. |
| `pb` | `numeric(8,2)` | YES | `null` | Price-to-Book ratio. |
| `div_yield` | `numeric(8,4)` | YES | `null` | Dividend yield as percentage (e.g., 8.5000 = 8.5%). |
| `payout` | `numeric(8,4)` | YES | `null` | Dividend payout ratio (e.g., 45.0000 = 45%). |
| `roe` | `numeric(8,4)` | YES | `null` | Return on Equity (percentage). |
| `refreshed_at` | `timestamptz` | NO | `now()` | When this row was last updated. |

**Notable absences:** Market cap, P/S ratio, EV/EBITDA. These can be added when needed. The current set covers the PSX screener's common filters.

**Data source:** DPS company detail pages. The `job_refresh_fundamentals` job runs every Sunday at 04:00 PKT.

| Column | Type | Nullable | Default | Notes |

### 4.7 `psx_index_eod` — Index end-of-day

**Purpose:** End-of-day values for PSX indices. Used for the index cards on the PSX landing page and the KSE-100 chart.

**Composite PK:** `(code, date)` — there is exactly one close per index per day. No surrogate `id` needed because no other table references this one by FK.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `code` | `text` | NO | — | **PK (composite).** Index code: `KSE100`, `KSE30`, `KMI30`, `ALLSHR`. |
| `date` | `date` | NO | — | **PK (composite).** Trading date. |
| `close` | `numeric(12,2)` | YES | `0` | Index close value. |
| `volume` | `bigint` | YES | `null` | Total volume (across all constituent stocks). |

**Why composite PK (not serial):** The business rule is "one row per (index, date)." Adding a serial PK would create a meaningless identifier. The natural key is compact enough (text + date = ~14 bytes) and never referenced by child tables.

**Data volume:** 4 indices × 250 trading days/year × 10 years ≈ 10,000 rows.

### 4.8 `psx_ticks` — Real-time trade tape

**Purpose:** Every individual trade tick from the AhleTrade feed. This is a high-write table — during active trading hours, the AhleTrade poller writes every trade as it happens.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | NO | `GENERATED BY DEFAULT AS IDENTITY` | PK |
| `symbol` | `text` | NO | — | Logical FK to `psx_market_snapshot.symbol`. |
| `time` | `timestamptz` | NO | `now()` | Trade timestamp from the exchange. |
| `price` | `numeric(12,2)` | YES | `null` | Trade price. |
| `volume` | `bigint` | YES | `0` | Trade volume (number of shares). |
| `created_at` | `timestamptz` | NO | `now()` | When the row was inserted (server timestamp). |

**Index:** `idx_psx_tick_sym_time(symbol, time DESC)` — tick chart query.

**REPLICA IDENTITY FULL:** This is critical for Supabase Realtime. With the default `REPLICA IDENTITY DEFAULT` (PK only), the WAL only contains the `id` column — not the price, symbol, or volume. `REPLICA IDENTITY FULL` tells Postgres to write all columns to the WAL, so Realtime broadcasts include the complete tick data.

**Data retention concern:** At ~500K rows per trading day, the `psx_ticks` table grows to ~10M rows in a month. Without a retention policy, this table will consume significant storage. Plan for a nightly cleanup job that deletes ticks older than 30 days.

**Usage:** Primarily for the AhleTrade poller to write tick data. The frontend subscribes to Realtime changes on this table for the time & sales tape display. The most recent tick per symbol is also used by the market snapshot refresh to update live prices between DPS polls.

### 4.9 `psx_signals` — ML signal cache

**Purpose:** Caches the output of the ML signal engine to avoid re-predicting on every page load. Each symbol gets one row, refreshed every 4 hours (or on-demand via the Python API).

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `symbol` | `text` | NO | — | PK. UNIQUE. 1:1 with `psx_market_snapshot.symbol`. |
| `signal` | `text` | NO | — | One of: `STRONG BUY`, `BUY`, `HOLD`, `SELL`, `STRONG SELL`. ⚠️ No CHECK constraint in current migration. |
| `confidence` | `numeric(5,2)` | NO | — | Model confidence percentage (0.00 - 100.00). |
| `probabilities` | `jsonb` | YES | `null` | Per-class probabilities from `predict_proba()`. Format: `{"STRONG BUY": 45.2, "BUY": 30.1, "HOLD": 15.3, ...}` |
| `features_used` | `text[]` | YES | `null` | Top 3 features that influenced this prediction (by importance score). |
| `model_version` | `text` | YES | `null` | Version string like `"1.0.0"` or `"fallback"`. |
| `predicted_at` | `timestamptz` | NO | `now()` | When the prediction was made. |

**Indexes:**
- `idx_psx_signals_confidence(confidence DESC)` — "top signals" query
- `idx_psx_signals_predicted(predicted_at DESC)` — stale detection (Python service checks if 4h TTL expired)

**How signals are generated:**
```
Frontend request ──► Python API /api/signal/HBL
  └─► Check psx_signals (is predicted_at < 4h old?)
        ├─ [fresh]: return cached signal
        └─ [stale]: run SignalEngine.predict(HBL)
              ├─ Fetch psx_ohlcv (last 300 bars)
              ├─ Fetch psx_fundamentals (PE for z-score)
              ├─ Compute 27 features (pandas/numpy)
              ├─ model.predict_proba(features)
              └─ UPSERT into psx_signals → return
```

**Why no CHECK on `signal`:** The original migration didn't include a constraint. Recommended Phase 1 fix: `ALTER TABLE psx_signals ADD CHECK (signal IN ('STRONG BUY','BUY','HOLD','SELL','STRONG SELL'))`.

### 5.3 `user_watchlist` — Active watchlist (v2)

**Purpose:** Stores the list of symbols a user wants to track. Used by the watchlist sidebar and the watchlist detail page.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | NO | `GENERATED BY DEFAULT AS IDENTITY` | PK |
| `user_id` | `uuid` | NO | — | FK → `auth.users(id) ON DELETE CASCADE`. |
| `symbol` | `text` | NO | — | Logical FK to `psx_market_snapshot.symbol`. |
| `added_at` | `timestamptz` | NO | `now()` | When the user added this symbol to their watchlist. |

**Uniqueness:** `UNIQUE(user_id, symbol)` — no duplicate symbols in one user's watchlist.

### 5.4 `price_alerts` — Active price alerts (v2)

**Purpose:** User-defined price alert rules. When the condition is met (checked by `job_check_alerts` every 60 seconds), the alert fires: `triggered_at` is set, `enabled` is flipped to false, and a notification is generated.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | NO | `GENERATED BY DEFAULT AS IDENTITY` | PK |
| `user_id` | `uuid` | NO | — | FK → `auth.users(id) ON DELETE CASCADE`. |
| `symbol` | `text` | NO | — | Logical FK to `psx_market_snapshot.symbol`. |
| `condition` | `text` | NO | — | **CHECK** `IN ('above','below','cross_above','cross_below')`. |
| `price` | `numeric(14,2)` | NO | — | Trigger price. Precision 14, scale 2 to handle all PSX price levels. |
| `enabled` | `boolean` | NO | `true` | Whether this alert is actively being evaluated. |
| `triggered_at` | `timestamptz` | YES | `null` | When the alert was last triggered (null = not yet triggered). |
| `created_at` | `timestamptz` | NO | `now()` | |

**Indexes:**
- `idx_price_alerts_user(user_id)` — user's alert listing
- `idx_price_alerts_enabled(enabled) WHERE enabled = true` — partial index for the alert-check job (only scans active alerts)

**Condition semantics:**
| Condition | Triggers when |
|---|---|
| `above` | snapshot price > alert price |
| `below` | snapshot price < alert price |
| `cross_above` | previous snapshot price ≤ alert price AND current > alert price |
| `cross_below` | previous snapshot price ≥ alert price AND current < alert price |

The `cross_above`/`cross_below` conditions require the alert-check job to track the previous snapshot price. This is handled in the Python service using an in-memory cache of the last-known prices per symbol.

**Alert lifecycle:**
```
1. User creates alert: symbol=HBL, condition=above, price=150.00
2. job_check_alerts (60s): reads all enabled=true alerts
3. For each alert: compare psx_market_snapshot.price vs alert.price
4. If condition met:
   a. UPDATE price_alerts SET triggered_at = now(), enabled = false
   b. INSERT INTO in_app_notifications (kind='price_alert', title='HBL crossed 150.00', ...)
   c. (future) Send email/push notification
```

**Purpose:** Stock positions within a portfolio. Each row represents one stock in one portfolio.

**Column detail:**

| Column | Type | Nullable | Default | Notes |
|---|---|---|---|---|
| `id` | `bigint` | NO | `GENERATED BY DEFAULT AS IDENTITY` | PK |
| `portfolio_id` | `bigint` | YES | `null` | FK → `psx_portfolios(id) ON DELETE CASCADE`. ⚠️ Nullable in SQL (should be NOT NULL). |
| `symbol` | `text` | NO | — | Logical FK to `psx_market_snapshot.symbol`. |
| `shares` | `bigint` | NO | `0` | Number of shares held. |
| `avg_cost` | `numeric(12,2)` | NO | `0` | Average cost basis per share (total cost / shares). |
| `purchased_at` | `date` | YES | `null` | Date of first purchase. |

**Uniqueness:** `UNIQUE(portfolio_id, symbol)` — a stock appears at most once per portfolio. Multiple lots are merged into one row (avg_cost = weighted average of all purchases).

**RLS** (via parent portfolio):
```sql
FOR ALL TO authenticated
USING (
  EXISTS (
    SELECT 1 FROM psx_portfolios
    WHERE psx_portfolios.id = psx_holdings.portfolio_id
    AND psx_portfolios.user_id = auth.uid()
  )
)
```

**Why RLS goes through the parent:** Holdings don't have a direct `user_id` column. The ownership check must go through `psx_portfolios.user_id`. This is a common Supabase pattern for child tables — the RLS policy joins to the parent to check ownership.

**PnL calculation (application-level):**
```
current_value = shares * psx_market_snapshot.price
cost_basis = shares * avg_cost
pnl = current_value - cost_basis
pnl_pct = (pnl / cost_basis) * 100
```

### 6.8 `finance_zakat_calculations` — Zakat (Islamic wealth tax)


## 12. RLS Policy Reference

### 12.1 Policy inventory (existing)

| Table | Operation | Policy | Role |
|---|---|---|---|
| `profiles` | SELECT | `USING (auth.uid() = id)` | authenticated |
| `profiles` | INSERT | `WITH CHECK (auth.uid() = id)` | authenticated |
| `profiles` | UPDATE | `USING (auth.uid() = id) WITH CHECK (auth.uid() = id)` | authenticated |
| All `psx_*` market data | SELECT | `USING (true)` | anon, authenticated |
| `psx_watchlist` (v1) | ALL | `USING (auth.uid() = user_id)` | authenticated |
| `psx_alerts` (v1) | ALL | `USING (auth.uid() = user_id)` | authenticated |
| `user_watchlist` (v2) | ALL | `USING (user_id = auth.uid())` WITH CHECK | authenticated |
| `price_alerts` (v2) | ALL | `USING (user_id = auth.uid())` WITH CHECK | authenticated |
| `psx_portfolios` | ALL | `USING (auth.uid() = user_id)` | authenticated |
| `psx_holdings` | ALL | `EXISTS (SELECT 1 FROM psx_portfolios WHERE id = psx_holdings.portfolio_id AND user_id = auth.uid())` | authenticated |

### 12.2 RLS patterns explained

**Pattern 1: Direct ownership** — Most user-owned tables have a `user_id` column and RLS checks `auth.uid() = user_id`. This is the standard Supabase pattern.

**Pattern 2: Ownership via parent** — `psx_holdings` doesn't have a `user_id` column. Its RLS checks through the parent `psx_portfolios` table:
```sql
USING (
  EXISTS (
    SELECT 1 FROM psx_portfolios
    WHERE psx_portfolios.id = psx_holdings.portfolio_id
    AND psx_portfolios.user_id = auth.uid()
  )
)
```
This is necessary because holdings are nested under portfolios, not directly owned by users. An alternative would be to add `user_id` to `psx_holdings` (denormalization), but that would require keeping it in sync with the parent.

**Pattern 3: Public read** — Market data tables use `USING (true)`. Every user (authenticated or anonymous) can read. Only service_role can write.

**Pattern 4: Admin-only** — Planned for Phase 9. Tables like `audit_log`, `error_events`, `feature_flags` would have no RLS (service_role only) or a policy like `USING (EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND plan = 'Admin'))`.

### 14.1 Market overview

```sql
-- Top gainers (last 5 minutes)
SELECT symbol, price, change, change_pct, volume
FROM psx_market_snapshot
WHERE volume > 0
  AND refreshed_at > NOW() - INTERVAL '5 minutes'

SELECT symbol, price, change, change_pct, volume

  AND refreshed_at > NOW() - INTERVAL '5 minutes'

LIMIT 10;

SELECT symbol, price, change, volume
FROM psx_market_snapshot
WHERE refreshed_at > NOW() - INTERVAL '5 minutes'

LIMIT 10;
```

### 14.2 Stock detail page

```sql
-- Current quote + fundamentals + profile + signal
SELECT
  s.symbol, s.price, s.change, s.change_pct,
  s.volume, s.day_high, s.day_low,
  f.eps, f.pe, f.pb, f.div_yield, f.roe,
  p.name, p.sector, p.listed_shares, p.free_float,
  sg.signal, sg.confidence, sg.predicted_at
FROM psx_market_snapshot s
LEFT JOIN psx_fundamentals f ON f.symbol = s.symbol
LEFT JOIN psx_profile p ON p.symbol = s.symbol
LEFT JOIN psx_signals sg ON sg.symbol = s.symbol
WHERE s.symbol = 'HBL';

-- Recent announcements (for stock detail page)
SELECT id, posted_at, title, category
FROM psx_announcements
WHERE symbol = 'HBL'
ORDER BY posted_at DESC
LIMIT 10;

-- Dividend history (for stock detail page)
SELECT announcement_id, ex_date, payout_type, per_share, bonus_pct
FROM psx_dividends
WHERE symbol = 'HBL'
ORDER BY ex_date DESC
LIMIT 20;

-- OHLCV bars (for candlestick chart)
SELECT date, open, high, low, close, volume
FROM psx_ohlcv
WHERE symbol = 'HBL'
  AND date >= CURRENT_DATE - INTERVAL '1 year'
ORDER BY date ASC;
```

### 14.4 Portfolio PnL

```sql
SELECT
  po.name AS portfolio_name,
  h.symbol,
  h.shares,
  h.avg_cost,
  s.price,
  (h.shares * s.price) AS current_value,
  (h.shares * h.avg_cost) AS cost_basis,
  (h.shares * s.price) - (h.shares * h.avg_cost) AS pnl,
  CASE WHEN h.avg_cost > 0
    THEN ((s.price - h.avg_cost) / h.avg_cost) * 100
    ELSE 0
  END AS pnl_pct
FROM psx_holdings h
JOIN psx_portfolios po ON po.id = h.portfolio_id
JOIN psx_market_snapshot s ON s.symbol = h.symbol
WHERE po.user_id = auth.uid()
ORDER BY pnl DESC;
```

### 14.5 Sector heatmap

```sql
SELECT
  p.sector,
  COUNT(*) AS stock_count,
  ROUND(AVG(s.change_pct), 2) AS avg_change,
  SUM(s.volume) AS total_volume,
  SUM(s.price * s.volume)::BIGINT AS total_value
FROM psx_market_snapshot s
JOIN psx_profile p ON p.symbol = s.symbol
WHERE s.refreshed_at > NOW() - INTERVAL '10 minutes'
  AND p.sector IS NOT NULL
GROUP BY p.sector
ORDER BY total_value DESC;
```

```sql
  s.price AS snapshot_price
FROM price_alerts a
JOIN psx_market_snapshot s ON s.symbol = a.symbol
WHERE a.enabled = true
  AND a.triggered_at IS NULL;
```
